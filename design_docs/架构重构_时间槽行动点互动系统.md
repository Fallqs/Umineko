# 架构重构：时间槽、行动点与互动系统 — 实施计划 v5（架构与数据解耦）

> 原则：先做纯架构（代码框架、接口、流程），数据填充（物品、信息条目、数值）在架构完成后由设定文档驱动填入。

---

## 一、时间槽架构

### 目标
- `TIME_SLOTS` 共13个：DAWN + MORNING_1 + BREAKFAST + NOON_1/2 + LUNCH + AFTERNOON_1/2 + DINNER + SLEEP_CHECK + EVENING_1/2 + MIDNIGHT
- 其中10个可行动槽位（7自由 + 3饭点），每槽 **2轮** 令牌环
- 3个特殊槽位（DAWN/SLEEP_CHECK/MIDNIGHT）只判定，不触发令牌环

### 架构改动
- `time_engine.py`: `TIME_SLOTS`, `FREE_SLOTS`, `KEY_MEALS`, `SPECIAL_SLOTS` 常量重写
- `core.py`: `token_ring.run(..., rounds=2)` 统一为2轮

---

## 二、行动点架构

### 目标
- 每天 **26点**，`reset_action_points` 统一设为此值
- 调查2点，移动1-3点，发言0点，特殊动作（安抚2点、赠送1点）各自定义

### 架构改动
- `state.py`: `reset_action_points()` 方法参数化（默认26，可配置）
- `core.py`: 系统公告中行动点说明改为引用配置而非硬编码

## 三、信息前置条件架构

### 目标
- `location_info.json` 中的信息条目可包含可选的 `requires` 字段
- `requires` 结构：`{"info": [info_id列表], "items": [item_id列表]}`
- 未配置 `requires` 的默认无条件解锁
- 未满足时返回标准"一无所获"模板（由 GM Session 根据状态转译）

### 架构改动
- `config_loader.py`: `get_location_info` 返回包含 `requires` 的结构（若无则为空）
- `action_engine.py`: `execute_investigate` 增加 `check_requires(role, info_entry) -> bool` 接口
- 数据后填：具体哪些信息需要哪些前置条件

## 四、物品系统架构（核心框架）

### 4.1 GameState 新增字段
```python
inventory: Dict[str, List[Item]]          # 角色 -> 物品列表
item_registry: Dict[str, Item]            # 全局物品定义（运行时从配置加载）
taken_items: Set[str]                     # 已被取走的道具ID（用于空状态反馈）
```

`Item` 结构：
```python
@dataclass
class Item:
    item_id: str
    gm_desc: str          # GM Session 看到的真实描述
    player_desc: str      # User Session 看到的模糊描述
    item_type: str        # "consumable"(一次性) | "permanent"(线索)
    holder: str = ""      # 当前持有者角色名
    consumed: bool = False
```

### 4.2 获取接口
- `action_engine.execute_loot(role, location)`：调查地点时自动检查是否有可获取物品
- 物品是否可获取由配置中的 `item_for` 字段决定（为空则任何人可获取）
- 已获取的物品通过 `taken_items` 标记，后续调查同一地点返回空状态

### 4.3 流转接口
- `transfer_item(from_role, to_role, item_id)`：转赠/搜身/验尸时调用
- `consume_item(role, item_id)`：一次性物品使用后调用

### 4.4 效果接口（预留，数据后填）
- `check_item_effect(role, item_id, context)`：检查持有物品是否满足某前置条件
- 具体效果（解锁条目、开启机关等）在数据层定义，架构层只留钩子

### 架构改动
- `state.py`: 新增 `inventory`, `item_registry`, `taken_items`
- `config_loader.py`: 支持解析 `item`/`gm_desc`/`player_desc`/`item_type`/`item_for` 字段
- `action_engine.py`: 新增 `execute_loot` 接口
- `core.py`: `on_orchestration_request` 处理 `transfer_item` / `consume_item`

## 五、玩家互动系统架构

### 5.1 ParsedAction 扩展
```python
@dataclass
class ParsedAction:
    investigate: bool = False
    investigate_target: Optional[str] = None   # 调查玩家目标
    search_target: Optional[str] = None        # 搜身目标
    comfort_target: Optional[str] = None       # 安抚目标
    gift: Optional[dict] = None                # {"item_id": str, "target": str}
    shoot_target: Optional[str] = None         # 开枪目标
    autopsy: bool = False                      # 验尸
    speech: str = ""
    skip: bool = False
    next_move: Optional[str] = None
    duel_beatrice: bool = False
```

### 5.2 互斥规则
- 每轮至多选一项：**调查场景 / 调查玩家 / 搜身 / 安抚 / 赠送 / 开枪 / 验尸**
- 发言和移动意向可与任何选项组合
- `parse` 按优先级取第一个：`investigate_scene > investigate_player > autopsy > search > comfort > gift > shoot`

### 5.3 各动作执行接口（仅框架，数值后填）

| 动作 | 执行方法 | 消耗 | 成功判定 | 结果 |
|------|---------|------|---------|------|
| 调查场景 | `execute_investigate` | 2 | 无条件 | 解锁信息/获取物品 |
| 调查玩家 | `execute_investigate_player` | 2 | 50%（可配置） | 获得 observable |
| 搜身 | `execute_search` | 2 | 60% + GM判定 | 获得对方一件物品 |
| 安抚 | `execute_comfort` | 2 | 无条件 | 自己-2，对方+2 |
| 赠送 | `execute_gift` | 1 | 同地点 | 转移物品，正确对象+行动点（数值后填） |
| 开枪 | `execute_shoot` | ? | 需持有枪 | GM判定后果 |
| 验尸 | `execute_autopsy` | 2 | 需有尸体 | 获取死因线索+死者物品 |

### 5.4 搜身应对机制（框架）
- 被搜身方获得 `"search_alert": {"from": role, "round": current_round}` 状态
- 下一回合若未应对，获得 **额外回合**（`bonus_turn` flag）
- 应对方式由 GM Session 生成（"拒绝"、"交出某物"、"开枪反抗"等）
- orchestrator 只负责标记状态和 granting 额外回合

### 5.5 Observable 系统（框架）
- `GameState.player_observables: Dict[str, str]`
- agent_wrapper action 发送后，GM Session 生成 observable 并通过 orchestration_request 提交
- 架构层只定义存储接口，模板内容后填

### 架构改动
- `action_engine.py`: 扩展 `ParsedAction`、新增各 `execute_*` 接口
- `state.py`: 新增 `player_observables`、`search_alert`、`bonus_turn`
- `agent_wrapper.py`: action 发送后请求 GM 生成 observable
- `core.py`: `on_action_received` 分发到各 execute 方法

## 六、turn_token 动态注入架构

### 目标
Orchestrator 在发送 turn_token 时，动态计算并注入当前可用的特殊行动列表：
- 同场其他角色（用于调查玩家/搜身/安抚）
- 当前持有物品（用于赠送）
- 是否有尸体（用于验尸）
- 是否持有枪（用于开枪）

### 架构改动
- `token_ring.py`: `turn_token` 消息格式扩展 `available_actions` 字段
- `core.py`: 构建 turn_token 时调用 `_build_available_actions(role, location)`
- `agent_wrapper.py`: prompt 中渲染 `available_actions` 为选项列表
